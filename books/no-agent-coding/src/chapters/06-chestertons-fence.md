# 6. Chesterton’s Fence for Software

**Executive thesis:** If the purpose of a structure is unknown, the organization has observation but not authority to remove it.

## Legacy code is evidence

A strange directory, duplicated setting, old script, or awkward dependency may be obsolete—or may encode a constraint whose explanation was lost. Vibe coding and human refactoring share the same temptation: infer that the structure is unnecessary because its purpose is not obvious.

## UNKNOWN is a lawful result

No Agent Coding treats unknown meaning as a first-class state. Unknown does not imply keep forever, but it forbids pretending that lack of understanding is evidence of irrelevance. The correct transition is preserve → observe → reconstitute → admit or refuse. This turns Chesterton’s Fence from a slogan into an epistemic control.

## Reconstitution before modernization

ggen-legacy represents the front-end side of this strategy: world-as-found becomes bounded observations, public ontology mappings, explicit contradictions, and an admitted remainder where evidence is sufficient. Missing authority is not manufactured merely to keep a migration moving.

## Operating practice

Before deleting or rewriting legacy behavior, record the exact subject, observed consumers, runtime consequences, public contracts, and contradictory evidence. If the purpose cannot be established, preserve the fence and type the gap. Modernization should reduce unknowns before it removes structures.

## Diagnostic question

What legacy structure are you preparing to remove without being able to state why it exists?
