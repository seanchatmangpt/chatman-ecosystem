# 17. Deterministic Projection

**Executive thesis:** ggen is valuable not because it can emit code, but because it can make representation a deterministic consequence of admitted semantics.

## Projection instead of authorship

The conventional question is “who wrote this file?” The manufacturing question is “which O* and which μ produced this file?” Deterministic projection means the same admitted subject and manufacturer identity produce the same bounded artifact, or a typed refusal explains why not.

## Topology is part of meaning

A locally correct API route in the wrong application directory is not a working route. Path ownership, package topology, interface placement, and generated/manual boundaries belong in the semantic contract. A model should not have to rediscover where a route belongs every time if the system already knows.

## One source, many surfaces

The same capability semantics can project to source code, CLI, HTTP, MCP, A2A, schemas, documentation, tests, workflows, policy and deployment targets. This is semantic DRY at enterprise scale: one admitted decision, many replaceable representations.

## Operating practice

Demand idempotency from the projector. Run manufacture twice against the same admitted subject and compare outputs. If drift appears without semantic input change, the manufacturing function is not yet deterministic enough for standing.

## Diagnostic question

Can the same admitted subject be manufactured twice with byte-identical or equivalently bounded output?
