# 69. Generate Every Marketplace Projection

## Manufacture broadly before selecting irreversible publication

Once the canonical product is admitted, generation should preserve as many lawful reversible market possibilities as practical. The cost of producing a candidate AWS listing, Microsoft plan projection, Oracle mapping, Salesforce package metadata, or Alibaba SaaS integration shape can be tiny compared with the cost of discovering incompatibilities during a real seller review.

This is DfCM applied to commerce:

```text
Admitted product graph
  → dependency-closed projection frontier
  → generate candidates in parallel
  → falsify cheaply
  → select publication targets later
```

## The marketplace set

For the running build, create bounded projections for:

- AWS Marketplace;
- Microsoft commercial marketplace;
- Google Cloud Marketplace;
- Oracle Cloud Marketplace;
- IBM catalog/partner surfaces;
- SAP Store/partner ecosystem;
- Salesforce AppExchange;
- ServiceNow Store;
- Red Hat/Kubernetes ecosystem;
- Snowflake Marketplace;
- Databricks Marketplace;
- Alibaba Cloud Marketplace.

The fact that a projection is generated does not mean the vendor, seller account, or product supports every commercial rail. Each pack emits a capability/gap manifest.

## Output bundle per market

A useful generated bundle includes:

```text
projection manifest
product/plan/listing metadata
vendor identifier mapping schema
commercial event adapter skeleton/implementation
meter projection where applicable
fulfillment/package artifacts where applicable
positive fixtures
negative fixtures
qualification plan
seller/review prerequisite manifest
support/legal metadata projection
receipt schemas
known extensions and losses
```

Different markets legitimately emit different subsets. Red Hat certification may emphasize artifact distribution rather than marketplace-native billing. Salesforce may emit managed-package/license artifacts. Snowflake may emit listing/share/application semantics. That is topology, not failure.

## Pin vendor source identity

Each pack records the vendor contract/documentation observation date or API/version basis used to manufacture it. A generated artifact without that source correspondence is difficult to requalify when the external system changes.

If official vendor material is ambiguous, the projection should preserve the unresolved edge as `UNKNOWN` and generate everything else that remains lawful.

## Gap manifests are first-class outputs

Examples:

```text
UNSUPPORTED:PRICING_MODEL
BLOCKED:SELLER_ENROLLMENT
UNKNOWN:PRIVATE_OFFER_AMENDMENT_SEMANTICS
LOSSY:CANONICAL_SUPPORT_TERM_NOT_EXPRESSIBLE
EXTENSION:VENDOR_SPECIFIC_CERTIFICATION
```

The generator does not “fix” a gap by changing canonical rights.

## No publication yet

At this stage every artifact is CONSTRUCT. Nothing creates a public listing, private offer, package in a production store, or financial transaction. Keeping generation non-consequential allows the system to explore the full market graph safely.

## Differential preview

Before qualification, normalize each generated plan projection and compare it back to the canonical plan. This catches obvious rights, meter, support, or lifecycle drift introduced by templates or mappings.

## Refusals

- `REFUSED:GENERATION_AS_VENDOR_SUPPORT`
- `REFUSED:MARKET_WITHOUT_SOURCE_CORRESPONDENCE`
- `REFUSED:GAP_HIDDEN_BY_TEMPLATE_DEFAULT`
- `REFUSED:UNREPRESENTABLE_RIGHT_SILENTLY_DROPPED`
- `REFUSED:GENERATOR_PUBLISHES_PRODUCTION_LISTING`

## Operational exercise

Generate candidate bundles for all twelve market families above. Produce one matrix whose cells show generated artifact, projection mapping, required vendor prerequisite, qualification gate, and current standing. The exercise succeeds even when several cells are `UNKNOWN`, `BLOCKED`, or `UNSUPPORTED`—provided those states are explicit and the canonical product remains unchanged.
